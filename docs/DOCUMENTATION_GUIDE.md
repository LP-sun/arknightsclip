# 文档写作指南

这份指南用于 README、操作手册、实验报告和命令行帮助文本，目标是让新贡献者快速上手，并降低功能变化后的维护成本。

## 写作原则

- 先说用途和结果，再给步骤、命令和注意事项。
- 用“默认/推荐/可选/实验性”标记成熟度，不把临时方案写成永久限制。
- 把必要边界写清楚，但避免无条件禁止；说明原因、影响和替代路径。
- 命令、路径、配置键使用代码格式；示例应能复制后按注释修改。
- 每个页面尽量只解决一个问题，并链接到相关的深入文档。

## 推荐结构

1. **简介**：一句话说明页面解决什么问题。
2. **前置条件**：只列真正必要的依赖，并说明可选替代方案。
3. **快速开始**：给出最短可运行路径。
4. **常用场景**：按任务而不是按模块组织命令。
5. **排错**：用“现象 → 优先检查项 → 解决办法”描述。
6. **限制与后续**：区分当前限制、已知问题和计划事项。

## 语气和限制性表述

优先使用“建议使用……；如果环境不同，也可以使用……”“默认会……，需要时可通过……调整”“该功能目前处于实验阶段，适合验证，不建议直接用于正式交付”。谨慎使用“必须”“严禁”“唯一”“永远不能”“不得以任何方式”。只有在安全、隐私、数据不可恢复或外部合规要求确实需要时，才使用绝对措辞；同时给出可行的替代操作。

## 更新检查清单

- 命令、路径和配置键是否仍存在？
- 示例是否泄露本机路径、账号或个人数据？
- 是否把实验性能力误写成稳定能力？
- 是否说明了失败时的恢复方式？
- 是否需要在 README、架构文档或报告索引中补充链接？
