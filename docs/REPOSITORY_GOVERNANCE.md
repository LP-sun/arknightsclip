# 仓库协作与治理指南

本文说明分支、提交、生成物和质量检查的推荐做法。规则以**可追溯、可恢复、便于协作**为目标；贡献者可以根据改动范围选择合适的流程。

## 分支与提交

- `main` 保持随时可用；小型文档修订、拼写修正和低风险配置调整可以直接提交。
- 涉及多个文件、行为变化或需要讨论的工作，建议使用 `feat/*`、`fix/*`、`chore/*`、`docs/*` 等短分支，再通过 Pull Request 合并。
- Pull Request 推荐至少有一次同行检查；实验性分支可先快速迭代，稳定后再整理提交记录。
- 合并方式不作强制规定：`merge`、`rebase`、`squash` 均可，优先选择容易保留上下文、方便回滚的方式。

## 高风险 Git 操作

涉及远程历史、未提交内容或大量文件的操作，先做备份或确认目标范围，并在提交说明中记录原因。强制推送、删除远程分支、批量清理、迁移 Git LFS，以及 `git reset --hard`、`git clean -fdx` 等命令都应谨慎使用。低风险、可逆的检查无需额外审批；不确定时优先使用新分支、临时目录或 `git stash` 保存现场。

## 质量检查

按改动范围运行检查：Python 或数据模型运行 `python tests/run_tests.py`；Rhine 渲染器在 `renderers/rhine/` 中运行 `npm test` 和 `npm run build`；仅文档改动则检查 Markdown 链接、代码块和命令是否与当前目录结构一致。CI 失败时，可以先合并不影响生产路径的文档或实验提交，但应记录失败原因和后续计划。

## 代码、数据与生成物

建议提交源文件、可复现配置和小型基准数据；大型或可再生文件按需放入 Release、对象存储或 Git LFS。`src/`、`scripts/`、`renderers/`、`psd2pen/`、`docs/` 可直接提交；`data/normalized/` 和 `data/manifests/` 提交能复现实验的版本；`generated/`、导出帧、视频和缓存默认不提交，但用于回归测试或交付验收时可附带精简样本并说明来源。本地路径、账号信息和玩家隐私应脱敏，可用 `*.example` 模板替代。

## 文档维护

文档应描述当前可用路径并明确实验性功能的成熟度。避免“永远”“绝不”“唯一正确”等难以维护的表述，改用“默认”“推荐”“当前版本通常”等措辞。具体约定见 [`DOCUMENTATION_GUIDE.md`](DOCUMENTATION_GUIDE.md)。

## 许可与素材

发布前请自行核对游戏素材、音乐、PSD 和第三方工具的授权条款；文档可以记录来源、用途和替代方案，但不替贡献者作法律判断。
